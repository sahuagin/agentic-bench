# On-demand tool/capability discovery without front-loading schemas — survey

Researcher memo, 2026-09-04 (mu-96ga9 follow-up). Operator facts taken as given: guidance in context is a suggestion; large contexts purge problem-solving.

## 1. Deferred / lazy tool loading — what actually triggers the lookup

- **Anthropic Tool Search Tool.** Deferred tools are excluded from the prompt entirely; the context contains only the search tool and non-deferred tools. Trigger = a schema-level stub plus the model's own sense of unmet need; docs only optionally suggest a prose line. Guidance: 3–5 hot tools non-deferred; use search at ≥10 tools or >10k tokens; selection accuracy degrades past 30–50 tools. Reported: Opus 4 49%→74%, Opus 4.5 79.5%→88.1%, 77K→8.7K tokens. https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool , https://www.anthropic.com/engineering/advanced-tool-use
- **Claude Code / Agent SDK.** Deferred tools listed *by name* in an `<available-deferred-tools>` block (~968 tokens vs 14–16k); a direct call to an unhydrated name fails with `InputValidationError`, fed back so the model calls `ToolSearch select:<name>`. Known failure: the model skips the search because it "knows" the name → failed call + retry. `ENABLE_TOOL_SEARCH=auto` defers at 10% of the context window. https://code.claude.com/docs/en/agent-sdk/tool-search , https://github.com/anthropics/claude-code/issues/31002 , https://github.com/anthropics/claude-code/issues/60052
- **OpenAI Responses `tool_search`.** Deferred functions keep name+description visible; it mostly defers the parameter schema; namespaces/MCP servers show only name+description. Recommends namespaces <10 functions. https://developers.openai.com/api/docs/guides/tools-tool-search
- **Agent Skills.** Level 1 = name+description (~100 tokens/skill) always in the system prompt; body loads only when the model decides to read SKILL.md. Trigger is prose matching, model-decided, no runtime gate. https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview
- **MCP and client-side layers.** Spec has only `tools/list` pagination and `list_changed`; no search primitive. Clients bolt it on: OpenCode `mcp_search`, Hermes Agent `tool_search`/`tool_describe`/`tool_call` with a names+short-description manifest degrading to names-only over budget; Anthropic's code-execution pattern (tool tree on a filesystem, 150k→2k tokens). https://modelcontextprotocol.io/specification/2025-06-18/server/tools , https://github.com/anomalyco/opencode/pull/12520 , https://hermes-agent.nousresearch.com/docs/user-guide/features/tool-search , https://www.anthropic.com/engineering/code-execution-with-mcp

## 2. Tool retrieval research — effect on accuracy and context

- **ToolLLM (16k APIs).** Trained retriever NDCG@5 84.9 vs BM25 17.0 vs Ada 45.4; with retriever pass 67.3 / win 63.1 vs oracle 66.7 / 60.0. Gorilla: the model must be trained/used *with* retrieved docs to profit. https://arxiv.org/html/2307.16789v2 , https://arxiv.org/pdf/2305.15334
- **ToolRet (43k tools).** Off-the-shelf retrievers are weak: best nDCG@10 = 33.83; GPT-3.5 pass rate drops 11.4 points with retrieved vs oracle tools. Retrieval quality, not the stub, is the ceiling. https://arxiv.org/abs/2503.01763
- **AnyTool.** Hierarchical retriever + self-reflection: +35.4 pts pass rate over ToolLLM. https://arxiv.org/abs/2402.04253
- **RAG-MCP (base qwen-max).** Harness-side retrieval before the model sees tools: accuracy 13.62% → 43.13%; prompt tokens 2,134 → 1,084. >90% success when the right tool is within ~30 candidates, collapse beyond ~100. The model never has to *ask*; the harness selects. https://arxiv.org/html/2505.03275
- **Weak/open models with retrieval tools.** TheMCPCompany: GPT-5 with retrieval ≈ ground-truth tools, but smaller models cannot exploit retrieval. Hermes docs: smaller models write poor search queries and substitute visible core tools (running `gh` in the terminal instead of searching for the deferred GitHub tool) — the substitution pattern in our battery. EcoAct (names list + `tool_register` meta-tool) cut cost 25–49% at unchanged pass rate, but only on GPT-4o/4-turbo. Less-is-More does harness-side selection for 7–8B models: ask the model *without tools* what it needs, then kNN picks real tools. Sub-7B models ignore prompt framing. https://arxiv.org/abs/2510.19286 , https://arxiv.org/html/2411.01643 , https://arxiv.org/html/2411.15399v1 , https://arxiv.org/html/2603.11513

## 3. Context size degradation — numbers

- **Lost in the Middle.** U-shaped curve; accuracy degrades for information mid-context even for long-context models. https://arxiv.org/abs/2307.03172
- **NoLiMa (13 models).** At 32K, 11 of 13 fall below 50% of their short-context score (Llama 3.1 8B 76.7→22.6; Claude 3.5 Sonnet 87.6→45.7). CoT does not rescue it. https://arxiv.org/abs/2502.05167
- **BABILong.** Models effectively use only 10–20% of the context; decline steepens with reasoning complexity — the "problem-solving purge", not just recall. https://openreview.net/forum?id=u7m2CG84BQ
- **Chroma Context Rot (18 models incl. Qwen3).** Monotonic degradation with input length even on trivial tasks; a single distractor reduces performance; focused ~300-token context beats full ~113k history on every model. Anthropic frames this as a finite attention budget. https://www.trychroma.com/research/context-rot , https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- **Tool count specifically.** 49 tools 94% → 207 tools 64% → 417 tools 20% (Llama-3.1-70B, Granite-8B, ToolACE-8B); 741 tools = 127k tokens/request. Even Claude Sonnet 4.6 picks better from adaptive short lists (K≈2–7): 93.1% vs 87.1% at fixed K=5. https://vllm-sr.ai/blog/semantic-tool-selection/ , https://arxiv.org/html/2605.24660v1

## 4. Trigger design — what creates the unmet need

- **Visible stub alone** works for frontier models; for weaker ones the documented failure is not "can't search" but "doesn't": substitutes a visible tool or answers directly. https://hermes-agent.nousresearch.com/docs/user-guide/features/tool-search , https://arxiv.org/abs/2510.19286
- **Runtime refusal redirect** (call unhydrated name → error → search) is the only public trigger that fires *at the moment of need*. Requires the name to be visible; costs a round trip when the model skips the search. Claude Code's tracker proposes auto-hydrate-on-first-call. https://github.com/anthropics/claude-code/issues/60052
- **Prose forcing fails on 8–24B models.** IntentKV: "you MUST call search" + persona + preamble → Mistral-Small-24B zero tool calls (degenerate loops); "lack of propensity, not capability." Probing on Qwen3 1.7B–32B: the models *internally* know a tool is needed (probe AUROC 0.89–0.96) but fail to act; *prefilling* a steering sentence into the assistant turn worked where prompting did not. https://arxiv.org/html/2606.09916 , https://arxiv.org/html/2605.09252v1
- **API-level forcing is propensity-independent.** vLLM named `tool_choice` / `required` use structured outputs and work with any supported model; Anthropic `any`/`tool` prefill the assistant turn. Caveat for Qwen3 on vLLM: the JSON grammar can clobber the XML tool format — terrain-check. https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/tool_calling.md , https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools , https://github.com/vllm-project/vllm/issues/22132
- **Hooks** (PreToolUse deny with reason; SessionStart/UserPromptSubmit inject) are programmatic gates whose payload is still prose: refusal-redirects, not forcing. https://code.claude.com/docs/en/hooks

## Mapping onto mu (ranked: effect on qwen-class first, context cost second)

1. **Harness-side pre-selection per turn (RAG-MCP / Less-is-More).** mu runs the `discover`/`t4c` ranker itself on the user prompt (and re-runs on each new user message or unfamiliar tool error), injecting the top ≤5–7 tool schemas plus matching skill metadata into the tool list. Model sees core tools + `discover` stub + a small rotating relevant set; everything else deferred, including AGENTS.md prose. No propensity required — the only mechanism with evidence on a Qwen base (13.6%→43.1%) and on 7–8B models; cost ≈1–2k tokens, bounded by retrieval quality (keep the stub for second chances).
2. **Names manifest + hydrate-on-touch.** Tool list carries core tools, `discover`, and a names-only (or name + ≤8-word description) manifest of the rest (~10–20 tokens/tool). Any call to an unhydrated name is intercepted, auto-hydrated and re-executed (or refused with the top-3 `discover` matches). Creates the unmet need at the one point weak models reliably notice — a failed call; weakness is substitution via bash, which mechanism 1 mitigates.
3. **Forced first call via structured decoding.** On the first assistant turn (and after each new user message), set `tool_choice` to `discover`, then revert to auto. Guaranteed by grammar regardless of propensity; one round trip. Fires where scheduled, not at the moment of need; pair with a harness-generated default query if the model's is empty.
4. **Prefill steering.** For non-thinking Qwen, prefill the assistant turn with a fixed sentence committing to a discovery check before acting; cheap, provider-agnostic, moved Qwen3 1.7B–32B where prompts did not.
5. **Prose and Skills metadata as retrieval surface only.** Keep the short bootstrap line and ~100-token skill descriptions because mechanisms 1–2 search over them, not because they drive behaviour. Drop the 10 KB AGENTS.md from context: it pays the context-rot cost and, per the battery and IntentKV, buys no trigger.
